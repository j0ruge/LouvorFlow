# ADR-003: Pure frontend formatter for the WhatsApp message

## Status

Accepted

## Date

2026-04-11

## Context

The share feature needs to turn an `EventoShow` object into a string that
matches a fixed WhatsApp-markdown layout (see PRD §"Core Features →
WhatsApp-formatted message generator"). Both share paths — clipboard copy
and `wa.me/?text=…` — consume the same string.

We need to decide where the formatter lives and how it is tested. Three
locations were considered:

1. A pure utility module on the frontend
   (`packages/frontend/src/lib/whatsapp-share.ts`), unit-tested with Vitest.
2. Inline inside the React component that renders the share buttons.
3. A new backend endpoint `GET /api/eventos/:id/whatsapp-message` that
   returns `{ text: string }` and the frontend simply forwards it to
   clipboard / wa.me.

## Decision

The formatter is a pure function exported from
`packages/frontend/src/lib/whatsapp-share.ts`:

```ts
export function formatEscalaWhatsApp(evento: EventoShow): string;
```

It is fully covered by Vitest unit tests in
`packages/frontend/src/lib/whatsapp-share.test.ts`, exercising: a fully
populated escala, songs without keys, songs without selected versions,
songs whose selected version has no link, members without functions, and
an empty escala. The share component imports the function and calls it
synchronously when the button is clicked.

The frontend test suite is bootstrapped as part of this task — Vitest is
already a project dependency via the backend, so the frontend just needs a
`vitest.config.ts` and a `test` script.

## Alternatives Considered

### Alternative 1: Inline inside the React component

- **Description**: The format logic lives directly in
  `EscalaShareActions.tsx`'s click handler.
- **Pros**: No new file; fastest to type out.
- **Cons**: Couples the format rules to React rendering, making it hard to
  test in isolation; future format changes (e.g., adding a section) become
  noisy diffs in the component file; the format — which is the heart of
  the feature — gets no automated coverage.
- **Why rejected**: The format is the most failure-sensitive part of the
  feature. It must be unit-tested, and unit-testable code wants to live
  outside React.

### Alternative 2: Backend endpoint `GET /api/eventos/:id/whatsapp-message`

- **Description**: A new backend route renders the string server-side.
  Frontend fetches it on demand and pipes it to clipboard / wa.me.
- **Pros**: Centralises domain logic in the backend; could be reused by a
  future cron / scheduled-broadcast feature.
- **Cons**: Adds a round-trip on every share click — defeats the snappy UX
  the PRD asks for; duplicates knowledge of EventoShow shape on the server
  in a second place; introduces a new endpoint that today serves a single
  client (the share button) and would need its own auth, validation,
  OpenAPI entry, and tests; the format generator is already going to be
  unit-tested either way, so the "centralisation" benefit is minor.
- **Why rejected**: Round-trip on every share contradicts the snappy
  UX goal and adds backend surface for no scaling reason.

## Consequences

### Positive

- The formatter is cheap to test, cheap to change, and decoupled from
  React.
- Sharing is instantaneous from the user's perspective — zero network calls
  on the click.
- The frontend gains its first Vitest configuration, unblocking future
  unit tests for other pure utilities.

### Negative

- A future "scheduled broadcast" feature that runs server-side would need
  its own server-side formatter (or a small shared package). This is
  acceptable: that feature does not exist yet, and the server formatter is
  ~40 lines of trivial string concatenation.

### Risks

- **Risk**: Two formatters drift if the server-side one is added later.
  **Mitigation**: When that feature lands, extract the formatter to a
  shared `packages/shared` location (does not exist yet) or duplicate with
  shared snapshot tests.

## Implementation Notes

- File: `packages/frontend/src/lib/whatsapp-share.ts`
- Tests: `packages/frontend/src/lib/whatsapp-share.test.ts`
- Vitest config: `packages/frontend/vitest.config.ts` with React Testing
  Library NOT required (the test target is a pure function).
- Add `"test": "vitest run"` and `"test:watch": "vitest"` to
  `packages/frontend/package.json`.
- Date formatting must use the project's existing date library (dayjs is
  already a transitive dep on the backend; the frontend can either reuse
  it or use `Intl.DateTimeFormat('pt-BR')` — TechSpec recommends the
  latter to avoid adding a frontend dep).
