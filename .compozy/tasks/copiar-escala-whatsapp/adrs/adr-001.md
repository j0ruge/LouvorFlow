# ADR-001: Per-escala song version selection over global primary version

## Status

Accepted

## Date

2026-04-10

## Context

The "Share Schedule to WhatsApp" feature needs to include a reference link
for each song in the shared message. In the LouvorFlow data model a song
(`musicas`) can have multiple registered artist versions
(`artistas_musicas`), and each version may carry its own `link_versao` (a
YouTube/Spotify/cifra reference). The current escala detail endpoint does
not return any link.

We need to decide how the shared message picks "the" link for a song that
has more than one version. Three product approaches were explored with the
user:

1. Always use the first version (oldest by `created_at`).
2. Prefer a version with `artista_id IS NULL` ("generic version"), then
   fall back to the first.
3. Let the worship leader pick which version applies to *this* escala when
   they add the song to the escala, persisted on the escala-song
   relationship.

The user explicitly chose option 3.

## Decision

The selected song version is stored on the escala-song relationship
(conceptually a new field on `eventos_musicas` referencing
`artistas_musicas`). The version picker UI lives on the song card inside
the escala detail / edit view, not on the global song catalog. Songs with
exactly one registered version auto-select that version with no UI prompt.
Songs with zero registered versions work fine — the shared message simply
omits the link line for them.

## Alternatives Considered

### Alternative 1: First version by `created_at`

- **Description**: The shared message uses the oldest version of the song.
- **Pros**: Zero UI work, zero schema change, deterministic, no per-escala
  state.
- **Cons**: The leader has no control. A song registered years ago with a
  bad link would forever appear with that link in shared messages.
- **Why rejected**: Removes leader agency in the exact place where it
  matters most — what link gets sent to the team this week.

### Alternative 2: Prefer "generic" (null artist) version, fallback to first

- **Description**: Use the version where `artista_id IS NULL` if it exists,
  otherwise the first version by `created_at`.
- **Pros**: No schema change; leverages an existing convention; gives a
  partial escape hatch (the leader can curate a "canonical" version).
- **Cons**: The convention is implicit — most leaders do not know it
  exists. Still no per-escala variation; the same song always shows the
  same link, even if used for two different services with different
  arrangements.
- **Why rejected**: Feels clever rather than clear, and hides a real
  product need (varying the version per service) behind a data convention.

### Alternative 3: Omit links in MVP

- **Description**: Ship the share feature without any links; messages
  contain only song name + key.
- **Pros**: Smallest possible scope; no backend or schema change.
- **Cons**: The user explicitly listed the link in the requested message
  format. Shipping without it ignores the brief.
- **Why rejected**: Misses the headline value the user asked for.

## Consequences

### Positive

- Worship leaders have full, explicit control over which link the team
  receives, per service.
- The share feature works correctly the first time without surprising the
  leader with an unfamiliar link.
- The version choice is data on the escala, so it is auditable and visible
  in the same place the leader manages everything else for that escala.
- Future features (e.g., per-version cifras export, rehearsal recordings)
  can reuse the same escala-song-version relationship.

### Negative

- Requires a schema addition on the escala-song relationship and a backend
  query change to surface the link in the escala detail response.
- Adds a small piece of UI (the version picker) on the song card inside
  the escala — only when ≥2 versions exist, but still net new UI.
- Existing escalas have no version selected; they will share with no link
  until the leader edits the escala once. (Acceptable since the prior
  baseline is "no share at all.")

### Risks

- **Risk**: Leaders ignore the picker and complain that the link is
  missing.
  **Mitigation**: When exactly one version exists, auto-select it so the
  vast majority of songs need no leader action.
- **Risk**: Backfilling existing escala-song rows with a sensible default.
  **Mitigation**: Field is nullable; no backfill required. Future edits
  set it lazily.

## Implementation Notes

- The schema change lives on the escala-song relationship (conceptually
  `eventos_musicas.fk_artistas_musicas` nullable). TechSpec to confirm
  exact column name and FK constraints.
- The escala detail endpoint must include the selected version's
  `link_versao` so the share message can be built client-side without an
  extra round trip.
- The version picker UI lives on the song card already rendered in
  `EventoDetail.tsx`. TechSpec to specify exact placement (inline select
  vs. dropdown menu).
