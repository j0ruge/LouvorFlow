# ADR-002: Inline `Artistas_Musicas` versions in the EventoShow response

## Status

Accepted

## Date

2026-04-11

## Context

The "Share Schedule to WhatsApp" feature requires that, for every song in an
escala, the worship leader can pick which `Artistas_Musicas` row applies for
that escala (per ADR-001). The picker UI lives on the song card inside the
escala detail page and must list every available version of the song so the
leader can choose between them.

We need to decide how the frontend obtains the list of available versions for
each song shown on the page. Three approaches were considered:

1. Inline the version list inside the existing `EventoShow` response.
2. Add a new endpoint `GET /api/musicas/:id/versoes` and fetch on demand from
   the picker.
3. Add a bulk endpoint `POST /api/musicas/versoes` that accepts a list of
   `musicas_id`s and returns versions for all of them in one request.

Practical scale: an escala has roughly 4-10 songs and a song typically has
1-5 versions. The total payload growth is bounded — at the upper bound,
~50 version rows of mostly small fields (id, artist name, link).

## Decision

The `EVENTO_SHOW_SELECT` Prisma include is extended so each
`eventos_musicas` row returns:

- The selected version (`artistas_musicas_evento_fkey`) as a single nested
  object with `{ id, artista_nome, link_versao }` (nullable).
- The full list of available versions for that song
  (`musicas.Artistas_Musicas`) as `versoes_disponiveis: Array<{ id,
  artista_nome, link_versao }>`.

The `formatEventoShow` service flattens these into the existing
`MusicaEvento` shape with two new fields: `versao_selecionada` and
`versoes_disponiveis`. The frontend renders the picker entirely from this
data — no extra round-trips. The PATCH version-update endpoint refetches the
escala detail (existing invalidation pattern) so the cache stays consistent.

## Alternatives Considered

### Alternative 1: New endpoint `GET /api/musicas/:id/versoes`

- **Description**: EventoShow stays lean. The picker fetches the version
  list lazily when the user opens the popover, or eagerly via React Query
  prefetch.
- **Pros**: Smaller default payload; cleaner REST surface; the version list
  becomes a reusable resource for unrelated features.
- **Cons**: N+1 fetches when the leader opens the page and clicks several
  pickers in quick succession; extra route + controller + service +
  repository + hook + cache key for marginal benefit; UI must handle a
  loading state inside the popover.
- **Why rejected**: The data is small enough that paying one extra request
  per click is worse than paying a few KB once. The reusable-endpoint
  argument is hypothetical — no other feature needs this list today.

### Alternative 2: Bulk endpoint `POST /api/musicas/versoes`

- **Description**: Frontend collects all `musicas_id`s in the escala and
  asks for versions in a single round trip after the EventoShow loads.
- **Pros**: Avoids N+1; keeps EventoShow lean.
- **Cons**: Two round-trips instead of one (the EventoShow + the version
  bulk); introduces a "bulk lookup" pattern that does not exist anywhere
  else in this codebase, increasing surprise; client code must coordinate
  the second request and handle its loading state separately from the
  page load.
- **Why rejected**: Same end-state cost as Alternative 1 but with extra
  client orchestration.

## Consequences

### Positive

- Single round-trip from page open to fully-rendered picker — the leader
  never sees a spinner inside the popover.
- The EventoShow response remains the single source of truth for everything
  the escala detail page renders.
- The picker, the message generator, and the version selection mutation all
  read the same data shape, so refactors stay localised.
- Server-side selection is bounded: a Prisma `select` projection cannot
  accidentally include cifras/lyrics blobs.

### Negative

- The EventoShow payload grows. Worst-realistic case (10 songs × 5 versions
  × ~120 bytes per version) is well under 10 KB extra.
- Adding versions to a song does not update an open escala detail page until
  the user refetches — acceptable; this is already true for several other
  fields and React Query invalidation handles the common cases.

### Risks

- **Risk**: Future songs accumulate dozens of versions, causing payload
  bloat.
  **Mitigation**: The Prisma `select` only returns three small fields per
  version. If a single song ever exceeds, say, 20 versions, we revisit by
  capping or paginating server-side.

## Implementation Notes

- Add a one-line `select` extension to `EVENTO_SHOW_SELECT` in
  `packages/backend/src/types/index.ts` that includes both the FK relation
  and the parent music's `Artistas_Musicas` collection.
- `formatEventoShow` in `eventos.service.ts` flattens the shape — no new
  service needed.
- Update `MusicaEventoSchema` in
  `packages/frontend/src/schemas/evento.ts` to add the two new fields.
- The OpenAPI spec for `GET /api/eventos/:id` must be regenerated to
  reflect the new fields.
